## 1. Skills de dominio — el hallazgo principal

Lo que se buscaba: las mejores skills de repositorios oficiales o de la comunidad para trabajo
de **middle, front y base de datos**, para incorporarlas.

### 1.1 El estándar es portable, y eso lo cambia todo

**Agent Skills** es un estándar abierto creado por Anthropic y publicado el **18/12/2025**.
Un `SKILL.md` con frontmatter (`name`, `description`) y instrucciones en markdown, más
subdirectorios opcionales de scripts, referencias y plantillas. Lo adoptaron Codex CLI en
semanas y Google Antigravity en enero de 2026; hoy funciona en Claude Code, Codex, Antigravity,
Gemini CLI, Cursor, GitHub Copilot, OpenCode, Windsurf y más de 30 superficies.

**Consecuencia para esta plantilla**: una skill de dominio bien escrita **no hay que
triplicarla por IDE**. Es el mismo fichero. Esto es la diferencia con los *agentes*, cuyo
frontmatter sí cambia por superficie (ver baseline anterior §1).

Fuentes: [estándar Agent Skills](https://codex.danielvaughan.com/2026/05/05/agent-skills-open-standard-portable-skills-codex-cli-cross-agent/) ·

### 1.4 Decisión de adopción

Con 107 000 skills descubribles, el riesgo dejó de ser la escasez y pasó a ser la **selección**.

| Decisión | Motivo |
|---|---|
| **Las skills de dominio propias (`/middle`, `/front`, `/bbdd`) son agnósticas de stack** | El método —SOLID, patrones, TDD, fronteras— no caduca cuando cambias de framework. Las skills de fabricante sí |
| **Las skills de fabricante se declaran, no se copian** | Vendorizar el `SKILL.md` de Vercel crea una copia que envejece en silencio y arrastra su licencia. Se declaran en [`.sdd/external-skills.json`](../../.sdd/external-skills.json) con referencia fijada y se instalan con `npx skills add` |
| **Ninguna se instala por popularidad** | Toda skill externa pasa auditoría: licencia, permisos que pide, dependencias, scripts que ejecuta, colisión de triggers con las nuestras. Registro en [`docs/agents/SKILLS-EXTERNAS.md`](../agents/SKILLS-EXTERNAS.md) |
| **Se descarta instalar colecciones completas** | Confirma la decisión del baseline anterior: colisiones de triggers, consumo de contexto y superficie de ejecución |

Riesgo específico y vigente: **ASI04, cadena de suministro agéntica**. Una skill es
instrucciones que tu agente obedece más un directorio de scripts que puede ejecutar. Es
dependencia ejecutable, y se trata como tal: referencia fijada, revisión del diff al actualizar,
y nunca `latest`.

## 2. TDD y QA con agentes — qué ha cambiado

### 2.1 El dato que justifica los gates

- DORA mide un **descenso del 7,2 % en estabilidad** de entrega asociado a la adopción de IA sin
  fundamentos de ingeniería sólidos. La penalización en *throughput* ya no se sostiene de forma
  uniforme —a nivel de equipo la correlación es positiva—, pero **el efecto negativo sobre
  estabilidad persiste**. ([InfoQ sobre el informe DORA](https://www.infoq.com/news/2026/05/dora-roi-ai-assisted-dev-report/))
- **52 %** de los QA encuestados reportan más volumen de bugs desde que se generaliza el código
  asistido; los PR generados por IA presentan **1,7× más incidencias**.
  ([DeviQA, State of AI-Generated Code 2026](https://www.deviqa.com/blog/state-of-ai-generated-code-2026-the-qa-and-testing-gap/))

Lectura: la velocidad no es el cuello de botella; la **verificación** lo es. Un gate que
ejecuta —`scripts/check-sdd.mjs`, la suite, el linter, el escáner— vale más que cualquier
instrucción en un prompt.

### 2.2 Lo que confirma nuestro §6 de AGENTS.md

- **El humano posee la especificación; el agente posee la implementación.** El test se escribe
  antes precisamente para que el agente no valide sus propios errores.
- **Dale al agente una forma de verificar su trabajo.** Es la palanca de mayor impacto sobre la
  calidad final; un bucle de realimentación ejecutable multiplica el resultado.
- **Mutation testing es el único indicador que detecta tests que mienten.** Muchos tests
  generados por LLM tienen cobertura presentable y *mutation score* bajo: no detectan defectos
  inyectados. Herramientas: **Stryker** (TypeScript), **mutmut** (Python).
- Ratio test:código sano en proyectos con TDD real: **1:1 a 1,5:1**.

Fuentes: [TDD con agentes — QASkills](https://qaskills.sh/blog/tdd-ai-agents-best-practices) ·
[Forbes Tech Council, 04/2026](https://www.forbes.com/councils/forbestechcouncil/2026/04/15/the-most-ignored-practice-in-ai-coding-test-driven-development/) ·
[Endor Labs, test-first prompting](https://www.endorlabs.com/learn/test-first-prompting-using-tdd-for-secure-ai-generated-code).

### 2.3 Lo que se incorpora

| Cambio | Dónde |
|---|---|
| Mutation testing con umbral declarado en el core, no solo cobertura | `docs/quality/TEST-STRATEGY.md`, skills `/middle` y `/front` |
| Revisión específica de código generado por IA en la fase de verificación | `.claude/agents/code-reviewer.md` |
| El *mutation score* del core como dato en `evidence.md`, no como adjetivo | `/sdd-verify` |

**No se incorpora**: TDAD (dos agentes, uno compila especificaciones a tests y otro itera la
implementación). Es prometedor y encaja con nuestro circuito, pero a fecha de corte es propuesta
académica sin implantación verificada. Queda anotado como línea de trabajo, no como práctica.
([arXiv 2605.01160](https://arxiv.org/pdf/2605.01160))

## 3. Arquitectura — corrección de un eje

El baseline anterior colocaba `vertical slice` en el eje **Dependencias**, junto a layered,
hexagonal y clean. La literatura de 2026 lo separa con un argumento que sostiene:

- **Macro arquitectura**: cómo se descompone el sistema en módulos con fronteras — bounded
  contexts, contratos, propiedad del dato, comunicación. Aquí vive *monolito modular*.
- **Micro arquitectura**: cómo se organiza el código **dentro** de una frontera — carpetas por
  feature, forma del handler, localidad del cambio. Aquí vive *vertical slice*.

Son **ejes independientes**, y la micro arquitectura es una **decisión local de cada módulo**:
el módulo de facturación no está obligado a organizarse por dentro como el de notificaciones.

Fuentes: [Modules vs Vertical Slices, 2026](https://appscale.blog/en/blog/modules-vs-vertical-slices-macro-vs-micro-architecture-modular-monolith-2026) ·
[Milan Jovanović](https://www.milanjovanovic.tech/blog/where-vertical-slices-fit-inside-the-modular-monolith-architecture) ·
[Fundamentals of Software Architecture, 2.ª ed., cap. 11](https://www.oreilly.com/library/view/fundamentals-of-software/9781098175504/ch11.html).

**Cambio aplicado**: `AGENTS.md` §3.1 pasa de seis ejes a **seis ejes macro + un eje micro
explícito**, y `docs/architecture/DECISION-GUIDE.md` pregunta por la organización interna
después de fijar las fronteras, no en la misma decisión. La *ley del proyecto* no cambia:
monolito modular con fronteras hexagonales sigue siendo el punto de partida, y el respaldo
bibliográfico es mayor que hace un año.

## 4. Priorización — MoSCoW con las reglas de verdad

MoSCoW forma parte del **DSDM Agile Project Framework** del Agile Business Consortium. Lo que
casi siempre se aplica mal:

| Categoría | Regla real |
|---|---|
| **Must have** | ≤ **60 %** del esfuerzo estimado del equipo. Por encima de eso hay riesgo de previsibilidad, salvo tecnología conocida, equipo estable y riesgo externo bajo |
| **Should have** | ~20 % del esfuerzo. Doloroso omitirlo, pero hay alternativa |
| **Could have** | ~20 % del esfuerzo. Es la **contingencia deliberada**: lo que se sacrifica cuando aprieta |
| **Won't have this time** | Se escribe. Un descarte no registrado vuelve como discusión |

**El reparto es sobre esfuerzo estimado, no sobre número de requisitos.** Diez "must" pequeños
y dos enormes no son el 83 % de must: hay que estimar. El reparto exacto lo acuerda cada equipo.

Fuente: [MoSCoW Prioritisation — Agile Business Consortium](https://www.agilebusiness.org/dsdm-project-framework/moscow-prioritisation.html).

**Cambio aplicado**: cada `RF` de `spec.md` lleva prioridad MoSCoW y estimación relativa, y
`/sdd-specify` calcula el reparto por esfuerzo y avisa si los must pasan del 60 %.

## 5. Delegación y aislamiento entre agentes

Verificado a raíz de una pregunta concreta: *¿los agentes se llaman de verdad unos a otros, y qué
impide que uno haga el trabajo de otro?* Son **dos preguntas distintas** y conviene no mezclarlas.

### 5.1 Delegación real: existe fuera de Claude Code

| Host | Cómo delega | Cómo se restringe a quién puede llamar |
|---|---|---|
| Claude Code | herramienta `Agent` en `tools` | `Agent(tipo)` en `tools` |
| **VS Code / Copilot** | herramienta **`agent`** en `tools` | propiedad **`agents: [...]`** en el frontmatter |
| **Cursor** (desde 2.4) | subagentes en `.cursor/agents/`, delegación **automática** según la `description` | `Agent(tipo)` en `tools` |
| Antigravity, Codex | por prompt: el mismo modelo adopta otro perfil | — |

Detalles que importan:

- En VS Code, `handoffs:` y delegación a subagente **son cosas distintas**: lo primero son botones
  que pulsa una persona al terminar una respuesta; lo segundo es el agente principal invocando a
  otro y recibiendo solo el resultado final. Coexisten.
- En Cursor, la `description` **es la señal de enrutado**: el agente principal la lee para decidir
  si delega. Descripciones vagas producen enrutado no determinista — un argumento real contra
  tener muchos agentes con terrenos solapados.
- Cursor admite además `readonly: true` (auditor que no puede escribir) e `is_background: true`.
- Los agentes en la nube de Cursor **no** pueden invocar subagentes: hay informes de fallo abiertos.

Fuentes: [Subagentes en VS Code](https://code.visualstudio.com/docs/copilot/agents/subagents) ·
[Agentes personalizados en VS Code](https://code.visualstudio.com/docs/agent-customization/custom-agents) ·
[Subagentes de Cursor](https://cursor.com/docs/subagents.md) ·
[Cursor 2.4](https://forum.cursor.com/t/cursor-2-4-subagents/149403).

### 5.1 bis · VS Code tiene hooks, y son compatibles campo por campo

Corrige el baseline anterior, que daba los hooks de VS Code por no verificados.

| | Claude Code | VS Code (preview) |
|---|---|---|
| Eventos | `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `SubagentStart`, `SubagentStop`, `Stop` | **los mismos + `PreCompact`** |
| Configuración | `.claude/settings.json` | `.github/hooks/*.json` **o `.claude/settings.json`** |
| Entrada por stdin | `session_id`, `cwd`, `hook_event_name`, `tool_name`, `tool_input`, `transcript_path` | **idéntica** |
| Salida | `hookSpecificOutput.permissionDecision` (`allow`/`deny`/`ask`) | **idéntica** |

**Consecuencia**: los hooks de esta plantilla funcionan en VS Code **sin cambios**, y con ellos la
guarda de territorio y la trazabilidad `observed`, que se creían exclusivas de Claude Code.

**Dos trampas identificadas**:

1. **No crear `.github/hooks/`.** VS Code cargaría la configuración dos veces —la suya y
   `.claude/settings.json`— y cada guarda se ejecutaría por duplicado en cada llamada. Es el mismo
   error que producía agentes repetidos en el selector.
2. **Los `matcher` son regex contra el nombre de la herramienta, y ese nombre cambia por host**
   (`Edit` vs `edit/editFiles`). Un matcher que no coincide **no dispara el hook**, y una guarda
   que no se ejecuta **falla en abierto**: permite todo en silencio. Los matchers se han ampliado
   para cubrir ambos vocabularios.

Fuentes: [Agent hooks en VS Code](https://code.visualstudio.com/docs/agent-customization/hooks) ·
[vscode-docs/hooks.md](https://github.com/microsoft/vscode-docs/blob/main/docs/agent-customization/hooks.md).

### 5.1 ter · Dónde busca cada host las skills

| Host | Ubicaciones |
|---|---|
| Claude Code | `.claude/skills/`, `~/.claude/skills/` |
| VS Code | `.claude/skills/` y `.agents/skills/` **de forma nativa**; más las de `chat.agentSkillsLocations` |
| Cursor | `.cursor/skills/`, `.agents/skills/` y, **por compatibilidad, `.claude/skills/` y `.codex/skills/`** |

**Conclusión**: una sola carpeta `.claude/skills/` sirve a las cuatro superficies. **No hay que
crear `.github/skills/` ni `.cursor/skills/`.** Es la diferencia práctica con los agentes, cuyo
frontmatter sí diverge y por eso necesitan envoltorio por host.

Fuente: [Agent Skills en Cursor](https://cursor.com/docs/skills.md).

### 5.2 El aislamiento no lo da el handoff

Un handoff hace que el trabajo **avance**; no impide que el agente que lo recibe escriba donde no
debe. El aislamiento se consigue con **herramientas** (quitar `Write`, quitar `agent`, lista
blanca) y con **rutas** (qué territorio es de quién).

**Cambio aplicado**: [`.sdd/territories.json`](../../.sdd/territories.json) declara el reparto, y
`guard-write.mjs` lo impone cruzando el agente activo con la ruta escrita. El agente activo lo
registran `SubagentStart`/`SubagentStop` en `.sdd/state/`, porque **`PreToolUse` no dice quién
escribe** — sin ese dato la guarda ve la ruta pero no la mano.

La regla es *"no entres en el territorio de otro"*, no *"quédate en el tuyo"*: en un proyecto
nuevo nadie sabe aún dónde vive cada cosa, y una guarda que bloquea lo desconocido se desactiva el
primer día.

## 5 bis. Calidad visual: el hueco que no cubren los gates de accesibilidad

Buscado a raíz de un requisito explícito: *que lo que salga de aquí no sea el típico MVP soso de
cuatro cajas*.

**El diagnóstico**: los gates de `/sdd-design` —seis estados, WCAG 2.2 AA, tokens, flujos con
error— garantizan que la interfaz **funcione**, no que tenga carácter. Son un suelo. Y hay un
sesgo documentado en contra: **la UI generada por un modelo converge en una estética genérica
reconocible**, y las skills de diseño de 2026 lo tratan como el problema central a resolver —la
de shadcn instruye explícitamente a *evitar la estética genérica de IA y tomar decisiones de
diseño intencionadas*.

**Skills verificadas para este terreno**:

| Skill | Publicador | Papel |
|---|---|---|
| `anthropics/skills:frontend-design` | Anthropic | Criterio visual antes de escribir código. ~277 000 instalaciones |
| `anthropics/skills:theme-factory` | Anthropic | Sistemas de tema: color, tipografía, claro/oscuro |
| `anthropics/skills:canvas-design` | Anthropic | Composición y maquetación |
| `anthropics/skills:web-artifacts-builder` | Anthropic | Prototipo autocontenido para validar dirección |
| `vercel-labs/agent-skills:web-design-guidelines` | Vercel | **Audita la UI terminada** contra las Web Interface Guidelines, en `fichero:línea` |
| `shadcn-ui/ui:shadcn` | shadcn | Componentes y registros; evita la estética genérica |

Instalación: `npx skills add vercel-labs/agent-skills --skill web-design-guidelines`.

**El patrón de publicación**, una vez visto, se explica solo:

| Terreno | Quién publica | Por qué |
|---|---|---|
| Diseño visual | Anthropic, shadcn, Vercel | Transversal, y vende producto o plataforma |
| Stack concreto | El fabricante | Vende su plataforma |
| **Método de ingeniería** | **nadie** | No hay negocio en ello |

**Cambio aplicado**: [`docs/design/DIRECCION-VISUAL.md`](../design/DIRECCION-VISUAL.md) como
artefacto vinculante que se decide **una vez** —igual que la constitución de arquitectura— y una
**puerta** en `/sdd-design`: sin dirección aprobada por el usuario, no se dibuja. Además, un
**elemento con carácter por pantalla** es obligatorio, `/front` verifica el código contra la
dirección, y `check-sdd --strict` falla si hay `design.md` con la dirección sin aprobar.

Las skills externas son el **refuerzo**, no el sustituto: siguen en `candidata` porque este
repositorio no tiene stack.

Fuentes: [Top skills de diseño frontend](https://top-agent-skills.com/top-skills-for-frontend-design) ·
[shadcn como agent skill](https://agenticskills.io/skills/shadcn) ·

## 6. Sin verificar / pendiente

Lo del baseline anterior §7 sigue vigente, más:

- Las skills de fabricante (Vercel, Supabase, Cloudflare, Netlify, Stripe, Neon) están
  **catalogadas y con referencia fijada, no auditadas una por una**: la auditoría toca cuando el
  proyecto adopte ese stack. `SKILLS-EXTERNAS.md` marca el estado real de cada una.
- `npx skills add` no se ha ejecutado en este repositorio: no hay stack todavía.
  `scripts/skills-sync.mjs` funciona en modo `--check` y **no instala nada sin confirmación**.
- El comportamiento de una misma skill entre superficies (Claude Code vs Codex vs Copilot) se
  documenta como portable según el estándar; **no se ha comparado la salida real** en cada una.
- Umbral de *mutation score* razonable por tipo de proyecto: no hay cifra defendible universal.
  Se declara en la constitución de cada proyecto.
- El nombre exacto de la herramienta de subagentes en VS Code: la documentación menciona
  **`runSubagent`** y **`agent`**, y el ejemplo de frontmatter que se cita usa `agent`. Aquí se ha
  declarado `agent`. **No se ha ejecutado** una delegación real en VS Code para confirmarlo.
- Los hooks de Cursor están escritos según su formato documentado, pero la guarda de territorio
  **solo se ha probado con el payload de Claude Code**. En Cursor debería funcionar igual porque
  `toolCall()` normaliza el payload plano; no está verificado en vivo.
- `readonly: true` e `is_background: true` de Cursor: documentados, no probados aquí.
